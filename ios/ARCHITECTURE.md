# CoreProp iOS — Architecture

A native SwiftUI client for the CoreProp backend (`https://coreprop.me`, a
FastAPI app fronting Supabase). This app is a **first-party companion** to the
existing web app / PWA: it reads the same REST API and authenticates against the
same Supabase project, so nothing on the server changes to support it.

## Layout

```
ios/
  ARCHITECTURE.md              ← this file
  README.md                    ← how to build / run / regenerate the project
  project.yml                  ← XcodeGen project definition (source of truth)
  CoreProp.xcodeproj/          ← generated by `xcodegen generate` (committed)
  CorePropKit/                 ← Foundation-only Swift package (models + logic)
    Package.swift
    Sources/CorePropKit/       ← library: models, networking, EV math, formatting
    Sources/CorePropKitVerify/ ← executable assertion runner (local verification)
  CoreProp/                    ← the SwiftUI app target
    App/                       ← @main, root shell, app state, app delegate
    Theme/                     ← design tokens + shared components (from :root)
    Features/                  ← one folder per screen
    Support/                   ← Info.plist, entitlements, Assets.xcassets
  CorePropTests/               ← XCTest suite (runs in Xcode; mirrors the verifier)
```

### Why a separate `CorePropKit` package

Everything platform-agnostic (models, the API client, the EV / payout math,
formatters) lives in `CorePropKit`, which is **Foundation-only** — no SwiftUI,
no UIKit. That lets it compile and run on a plain macOS toolchain, so the logic
can be verified without an iOS simulator:

```
cd ios/CorePropKit && swift build && swift run CorePropKitVerify
```

The machine this was built on had only Xcode **Command Line Tools** (no full
Xcode, no iOS SDK, and — importantly — **no XCTest**), so the runnable
verification is the `CorePropKitVerify` executable (plain `assert`-style checks),
not `swift test`. The `CorePropTests` XCTest suite is provided for use inside
Xcode, where XCTest is available.

## Backend contract (as of this writing)

Base URL: `https://coreprop.me`. All snake_case; the client decodes with
`.convertFromSnakeCase`.

### Auth — Supabase GoTrue (the web app uses supabase-js; native uses the REST API)

The FastAPI backend verifies a **Supabase JWT** as `Authorization: Bearer
<access_token>` (`web/auth.py`). The app authenticates directly against Supabase
Auth, exactly as supabase-js does under the hood:

- `POST {SUPABASE_URL}/auth/v1/token?grant_type=password` — sign in. Headers:
  `apikey: <anon>`, `Content-Type: application/json`. Body `{email, password}`.
  Returns `{access_token, token_type, expires_in, expires_at, refresh_token, user}`.
- `POST {SUPABASE_URL}/auth/v1/signup` — sign up. Body `{email, password,
  data:{username}}`. A `username` is stored in `user_metadata` (2–20 chars,
  letters/numbers/underscore; `/api/auth/check-username` validates uniqueness).
  If the project requires email confirmation, **no session** is returned until
  the user confirms.
- `POST {SUPABASE_URL}/auth/v1/token?grant_type=refresh_token` — refresh.
- `POST {SUPABASE_URL}/auth/v1/logout` (Bearer + apikey) — global sign-out.
- `GET  {SUPABASE_URL}/auth/v1/user` (Bearer + apikey) — current user.

`SUPABASE_URL` and the anon key are **not** hard-coded; the app fetches them at
launch from `GET /api/ui-config` (`{supabase_url, supabase_anon_key,
vapid_public_key}`), the native analogue of the web app's `window.__COREPROP_CONFIG`.

### The bet object (`BetResult.to_dict` + pipeline extras)

```
bet_id, player_name, league, prop_type, pp_line, fd_line, side, true_prob,
raw_true_prob, market_width, team, true_odds, edge, individual_ev_pct,
over_odds, under_odds, both_sided, start_time, odds_type,
fd_odds_book, dk_odds_book, pin_odds_book, nv_odds_book, bet_key
```

`in_backtest` is **not** on the payload — the client joins `bet_key` against
`GET /api/backtest/keys` locally (a `Set<String>`), matching the web app.

### Payout tables — must be mirrored (single ruler)

Power `{2:3, 3:6, 4:10, 5:20, 6:37.5}`; Flex `{3:{2:1,3:3}, 4:{3:1.5,4:6},
5:{3:0.4,4:2,5:10}, 6:{4:0.4,5:2,6:25}}`. There is **no 2-leg Flex** — it
degenerates to Power-2, so the client short-circuits `n == 2` to the Power-2
payout (matching `ev-page.jsx` / `page-backtest.jsx`). Per-leg EV is
`p / breakEven(n, type) − 1`. `BREAK_EVEN` is re-derived from the payouts in the
verifier (closed form for Power, bisection for Flex), the same contract
`tests/engine_tests/test_payout_table_mirror.py` enforces server-side.

## Subscription gating (402)

The backend gates paid payloads with **HTTP 402** only when
`BILLING_ENFORCE=true` *and* Stripe is configured (off by default). On any 402
the app fetches `GET /api/billing/status`; if `active == false` it routes to the
paywall and does not retry. `active` is the single unlock flag (a `comped`
account has `status == null` but `active == true`).

**Apple IAP note.** Payment is Stripe **web checkout** only (`/api/billing/checkout`
returns a hosted URL). App Store Review Guideline 3.1.1 forbids steering users
to external purchase flows for in-app digital content without an entitlement.
This app therefore ships as a **reader/companion**: it shows subscription
*status* and a "Manage on the web" affordance, but does **not** present an
in-app buy button. Adding StoreKit IAP (with server-side reconciliation) is a
documented follow-up, not part of this build.

## Notifications

The existing push feature is **Web Push (VAPID / pywebpush)**, tied to the
auto-backtest worker and the `push_subscriptions` table (`{user_id, endpoint,
p256dh, auth}`). That transport is browser-only and cannot deliver to a native
app. Native iOS needs **APNs**, which requires an Apple Developer Program
membership, an APNs auth key, a new server endpoint to register device tokens,
and a server-side APNs sender — none of which exist yet.

This app therefore implements the **client half honestly**: it requests
notification authorization, registers for remote notifications, captures the
APNs device token, and surfaces the permission state in Account. Server-side
APNs delivery is **not** wired; the token is not sent anywhere until a
`POST /api/push/apns/register` endpoint + `apns_tokens` table exist. See
README "Notifications" for the proposed server change. No notification is
claimed to be delivered that cannot be.

## Screens (native mapping of the 6 web tabs + account)

Five-tab `TabView` (iOS convention ≤ 5):

1. **Bets** — the `+EV Bets` board: league/prop/min-true% filters, sortable
   list, tap a row to add to the slip; logged rows tinted.
2. **Lines** — segmented `Combined / PrizePicks / Sportsbooks` (the three web
   board tabs), sortable per-book odds tables.
3. **Slip** — the Slip Builder / EV calculator (client-side Power/Flex EV +
   optional server correlation-aware `optimize`), plus "log to backtest".
4. **Backtest** — logged slips with client-recomputed outcomes + summary stats.
5. **Account** — profile, subscription status, notifications toggle, settings
   (auto-backtest prefs), a pushed **Performance/Analytics** screen, sign out.

Signed-out: an auth screen (log in / create account) over a branded landing.

## Design tokens

Dark-mode only. Ported verbatim from the `:root` block of `web/static/index.html`.
Load-bearing rules: `--primary #1E6FB0` is **fill/border only** (white text on it
clears AA); `--primary-2 #6FBCEC` is **text/icon only** (never white on it);
`--text-4 #4a4a59` is decorative/disabled only; hovers/pressed states **darken**;
no gradients on accent surfaces. Fonts: Inter (UI) + JetBrains Mono (all
numbers/odds/%); on iOS we use the system font for UI and a monospaced-digit
font for numbers, which reads the same without bundling web fonts.
